# Three-way comparison of LLM-based digital-twin / DES model generators

**Status:** protocol v1 — all three adapters integrated (C wired to the live
DigitalTwinBuilder service on 2026-09-17)
**Date:** 2026-09-08 (C integration 2026-09-17)
**Scope:** FactoryFlow (method **A**), LLM-DES-Modeling (method **B**), and a third method **C** = DigitalTwinBuilder (user-provided multi-agent service).

---

## 1. Objective and methods under test

We compare three approaches to automatically generating discrete-event simulation
(DES) models of manufacturing systems ("digital twins"). Each method is used as
published — **no behavioural changes to the tools** are allowed. Only orchestration
(process invocation, I/O conversion, result parsing) lives in this harness.

| Method | Repo | Input it consumes natively | Output it produces |
|---|---|---|---|
| **A** | `FactoryFlow/FactoryFlow_v2` | Natural-language description of the system | Python source defining a parameterised FactorySimPy component network |
| **B** | `LLM-DES-Modeling` | CSV event log of the plant (pm4py process mining) | Python source of a self-contained SimPy model |
| **C** | `DigitalTwinBuilder` (remote FastAPI service) | an **interview**: the method asks questions in Russian and a customer answers (no file input) | a requirements JSON document, then a PostgreSQL schema (agent 1) and a PyChrono multi-physics script (agent 2) |

A and B route all LLM calls through OpenRouter (`OPENROUTER_API_KEY`) and are
executed inside their own virtualenvs with their own dependency sets (A: Python 3.13
venv, B: Python 3.11 venv). The harness never mixes the two environments in one
process; each method runs in a **separate subprocess**. C is not a local tool at
all: it is a service reached over HTTP (`config.yaml: C.*`, `dtb_repo`), and its
adapter is therefore stdlib-only.

### Comparison question

> Given the *same underlying system* (a synthetic plant with known parameters),
> which method produces a simulation model whose **behaviour** (throughput, WIP,
> utilisation, energy) best matches the behaviour of the real (ground-truth)
> plant, how **robustly** (across repeated generations), how **cheaply**
> (LLM calls / tokens / wall time), and with what **structural fidelity**
> (recovered parameters vs. known truth)?

## 2. Fairness principles

1. **Native inputs.** Each method receives the input its authors designed for:
   A a prose description, B an event log, C whatever its adapter declares. Every
   case bundle therefore contains *per-method native inputs that describe the same
   plant*.
2. **Single-shot generation (baseline).** The primary measurement is one
   generation pass per method per case: A: `run_amg_wrapper(description)`; B:
   `ModelBuilder.build(...)`. Neither method's closed-loop machinery
   (A: `run_manual_overrides`, B: `Modeloptimizer`/`Modeladaptor`) is used in the
   baseline — see *steered mode* (§7.4) for the optional second stage.
3. **No re-rolling.** A failed or poor generation is recorded as a failure, never
   retried for a better sample. Success rate is itself a metric.
4. **Seeding.** Every stochastic element (truth simulation, each method's model run,
   LLM sampling where controllable) is seeded from one case-level base seed so runs
   are reproducible. LLM sampling is NOT temperature-pinned — repetition therefore
   measures genuine generator variance.
5. **Autonomy.** Human-in-the-loop prompts that a method would normally issue are
   answered deterministically by the harness (or counted as an autonomy penalty).
   Any method that *requires* a human to produce a runnable model is scored on its
   autonomy dimension accordingly.
6. **Isolation.** Methods execute in their own venv + `cwd`; side effects (files
   written by generated models, temp diagrams) stay inside a per-run workdir.

## 3. Case bundles

Directory: `cases/<case_id>/`. One self-contained, immutable bundle per plant.

| File | Purpose |
|---|---|
| `manifest.yaml` | machine-readable truth spec (below) |
| `manifest.json` | canonical JSON copy generated by `casegen.py` (adapters read this; zero-dep) |
| `eventlog.csv` | B's native input — synthesized plant log, `workingtest.csv` schema |
| `prompt_A.txt` | A's native input — prose/table description of the same plant |
| `aux_B.txt` | free-form context B needs beyond the log (buffer list + capacities, defect facts), mirroring `main.py`'s hand-written strings |
| `truth_kpis.json` | ground-truth KPI values (mean over reference replications) |
| `station_table.md` | per-station metrics table (identical definition to B's `metrics.compute`) |
| `truth_structure.json` | ground-truth structural parameter table (for structural scoring) |

Files that depend on a simulation (`eventlog.csv`, `truth_kpis.json`,
`station_table.md`, `prompt_A.txt`, `aux_B.txt`) are **generated deterministically**
by `python casegen.py cases/<id>` and committed with the case, so all three methods
always consume byte-identical inputs.

**C's native input is an interview, not a file.** C's UI agent asks the customer
questions; the harness answers them with an LLM responder (the harness-side
"plant engineer") whose only knowledge is `prompt_A.txt` plus the manifest's exact
parameter values, passed verbatim in its system prompt. The responder is therefore
the same information set that A receives in prose and B receives as a log — the
channel differs because the method's channel differs (§2.1). Every question,
answer and agent reply is logged to `artifacts/interview.log`, and the number of
interview turns is a reported **Autonomy** measurement (§6, §7.5).

**The engineer speaks first.** C's UI prompt is an interview protocol: it analyses
the user's answer, returns `completed: true` with the requirements once the
information suffices, and otherwise returns `completed: false` plus questions
(`system.py::UI`). A conversation holding nothing but the system prompt therefore
gives agent 0 nothing to analyse, so the harness posts the engineer's opening
statement — `prompt_A.txt` plus the manifest's exact parameter values, i.e. the
same information the responder would give in answer — as the first **user** turn
before any task is submitted (`_opening_message`). This is the information A and
B receive at the start, in the form C's own channel requires; it does not remove
C's work, because the agent must still elicit, parse and fill the requirements
schema from prose, and the turn count that scores Autonomy stays the agent's own
choice (a rep that asks follow-up questions still scores more turns than one that
completes immediately).

Because the customer is a person who always knows their own intent, the responder
also carries a short, fixed policy for the questions no case bundle can answer:
what the digital twin is *for* (monitor throughput, WIP, energy per part and
machine availability), how often data updates (per processed part; state intervals
continuously), and that alarm thresholds are undefined — in which case it asks C to
proceed with the parameters it already has. This text is byte-identical for every
case and repetition, contains no parameter values, and none of it is scored against
truth; without it C loops forever asking for goals (observed) and the run fails for
a reason that has nothing to do with its modelling ability. The policy is logged at
the head of each `interview.log`. It is *not* a licence to improvise: any other
missing fact is still refused.

### `manifest.yaml` (authoring format)

```yaml
case_id: case_0001_serial_line
title: 5-machine serial line, deterministic arrivals
description: |            # optional human sentence, not used as input
time_units: s             # all *_s fields below
reference:
  log_rep: 0              # which seeded replication becomes eventlog.csv
  replications: 10        # truth KPIs averaged over these
  warmup_s: 21600         # excluded from truth KPIs and log
  window_s: 432000        # measurement horizon after warmup
  seed: 20260908
arrival: {inter_arrival_s: 130}
machines:                 # listed in flow order
  - {id: M1, process_time_s: 150, availability: 0.98, mttr_s: 600,
     work_power_kw: 4.0, idle_power_kw: 0.4}
  # ...
buffers:                  # between consecutive flow elements
  - {id: B0, capacity: 20}   # source -> M1
  - {id: B1, capacity: 8}    # M1 -> M2
  # ...
# expected structural ground truth (used by report for param-recovery scoring)
truth_structure:
  machines: 5
  serial: true
```

Constraints (v1): serial production flow only; buffers have capacity; machines have
deterministic processing time; failures occur only while the machine is free (never
mid-processing), which keeps `Working` rows in the log equal to single-part
processing windows.

## 4. Ground-truth engine (`truth/`)

`truth/plant.py` is a small pure-SimPy plant used to (a) synthesise the event log
for B and (b) measure ground-truth KPIs. It is intentionally independent of both
tools' libraries. A plant is defined by a manifest. Failure schedules are
pre-drawn from the seeded RNG before the run (renewal process with `availability`
and `mttr_s`); a down window is only "honoured" while the machine is free, which
keeps per-part `Working` windows unbroken.

### Log synthesis — `eventlog.csv` schema (identical to `data/workingtest.csv`)

| Column | Content |
|---|---|
| `ID` | constant case id per log |
| `MachineName` | `M1`..`Mn` |
| `StartTime`, `EndTime` | ISO-8601 (`pandas.to_datetime`-parseable) |
| `ReasonCode` | `Working` (one row = one processed part), `Idle` (starved or blocked), `Stopped` (down) |
| `EnergyConsumption` | energy in the window, **kJ** (`kW · s`), matching the sample data unit |

Only the measurement window `[warmup_s, warmup_s + window_s]` is emitted.

### Ground-truth KPIs — `truth_kpis.json`

Averaged over `reference.replications` seeded runs (mean + std):

```json
{
  "throughput_per_hour": 26.4,
  "wip_parts": 14.2,
  "energy_per_part_kwh": 0.35,
  "utilization": {"M1": 0.91, "...": null},
  "per_machine": {
    "M1": {"working_s": null, "idle_s": null, "stopped_s": null,
           "processed": null, "availability": 0.97}
  }
}
```

Definitions: `throughput_per_hour` = completed parts / window hours;
`wip_parts` = time-average of parts inside buffers + machines;
`energy_per_part_kwh` = (Σ working·work_power + Σ idle·idle_power)/3600 kWh over the
window ÷ completed parts; utilisation = working time / window.

## 5. Unified output contract

Every method adapter writes the same `result.json`:

```json
{
  "method": "A", "case": "case_0001_serial_line", "rep": 0,
  "status": "ok | service_unavailable | generation_error | simulation_error | timeout | parse_error",
  "error": "optional traceback head",
  "elapsed_generation_s": 12.3, "elapsed_simulation_s": 2.1,
  "llm_calls": 2, "llm_tokens_estimate": null,
  "generated_model_file": "runs/.../model.py",
  "kpis": {
    "throughput_per_hour": 25.1,
    "utilization": {"M1": 0.90},
    "wip_parts": 13.8,
    "energy_per_part_kwh": null,
    "native": {"..." : "..."}          // method-specific extras, kept raw
  },
  "assumptions": "A only: reasoner assumptions text",
  "notes": ["..."]
}
```

`service_unavailable` is the one status that is **not** the method's: the remote
host did not answer at all, so the rep carries no signal about generation
behaviour and is read as deployment availability rather than a method failure. C
retries its reachability probe, reads, polls and session/conversation creation
(`C.net_retries`, `C.net_retry_delay_s`) before recording it; task submission is
never retried, because a repeat would bill the model twice. The validity table
enumerates the statuses actually present rather than a fixed column list, so a
failure cannot hide by not being named.

A transport failure of a dependency that is not C's endpoint is also recorded as
`service_unavailable`, with the dependency named in the note so the wrong host is
not blamed — currently the harness's own responder LLM at OpenRouter, whose
outage says nothing about C's generation behaviour either. An `HTTPError` is
never `service_unavailable`: the service answered, with an error, so it is
charged to C. Likewise a UI agent that replies in a dialect its own prompt
forbids (brace-less `completed: false` YAML instead of the mandated JSON object)
is a **generation** error — the agent answered, and answered off-contract.

**C's rep status is derived from its stages.** C's pipeline is several agents in
sequence (interview → DB schema → twin config / PyChrono script / DES model →
execute the DES model), and "the pipeline returned" is not the same fact as "the
method worked": an agent can answer off-contract, or return a model that will not
run. A rep is `ok` only when the DES slot produced a contract-bearing KPI
payload. Otherwise the verdict is taken from the deepest stage that failed:
executing the generated DES model exited non-zero → `simulation_error`; the
model exceeded its execution timeout → `timeout`; it could not be executed at all
→ `simulation_error`; it ran but printed no KPI contract → `parse_error`; no
model was produced → `generation_error`, or `service_unavailable` when the DT
agent's endpoint did not answer for that slot (§5's rule applied inside the
stage); a stage's task-poll timeout → `timeout`. The stage the verdict came from
is recorded as `native.status_basis` so the status is auditable against the
per-stage evidence in `native` (the `des_stage`, `dt_note`, `db_note` fields).
This matches A and B, which set `simulation_error` when the model they generated
exited non-zero; before this derivation, C reported `ok` for every one of those
outcomes, because `ok` meant only that its pipeline completed.

The rule lives in `adapters/base.py` (`derive_rep_status`) and both the adapter
and `report.py` apply it, so a rep recorded before the derivation is *rendered*
under its stage outcome rather than its stored `ok` — the validity table re-derives
each C row (showing `simulation_error (recorded \`ok\`)` in the per-rep table, so
the run's own `result.json` is not silently contradicted), and a rep whose stage
evidence cannot settle the verdict is shown as recorded with the reason. For that
to be possible the per-slot error strings are kept structured in
`native.dt_slot_errors`; a block written before 2026-09-20 has only the formatted
`dt_note`, which the report reads back best-effort (`des: …` segment) and refuses
to guess from when it names none. Under the derivation the two crashed models in
`runs/20260919_052152` are `simulation_error` and the third rep that reached the
stage is `service_unavailable`, so C's validity row for that run is 0 ok (see §8);
A's and B's rows are unaffected, as they already reported their model's failure.

A missing/non-numeric indicator is `null`, never fabricated. **Coverage matrix**
(which indicator each method can express) is part of the report:

| Indicator | Truth | A | B | C |
|---|---|---|---|---|
| throughput | ✔ | ✔ | ✔ | ✔ (DES slot, executed) |
| utilisation per machine | ✔ | ✔ | — | — |
| WIP | ✔ | approx (buffers) | ✔ (blueprint contract) | ✔ (DES slot, executed) |
| energy per part | ✔ | — | ✔ (kWh/part contract) | ✔ (DES slot, executed) |
| recovered structure | ✔ | ✔ | ✔ | ✔ (requirements + schema; DT config/script captured, not executed; DES model executed) |

Unit conventions: throughput in **parts/hour**; the FactoryFlow time unit is taken
as **seconds** (both tools' models are told so in their prompts; `config.yaml:
A.model_time_unit_s`). Energy in **kWh**. Asymmetries in coverage are themselves
comparison findings (model expressiveness), not errors.

**C's KPI coverage is conditional on the DES slot, and the yield is not
guaranteed.** C generates a *requirements document* and a *database schema*, plus
(via its agent 2) a twin configuration, a PyChrono multi-physics script and a
discrete-event SimPy model. Only the last is executable, and it carries B's own
stdout contract, so C's throughput/WIP/energy are populated exactly when that slot
yields a runnable model and are `null` otherwise — the coverage matrix above marks
them `✔ (DES slot, executed)` as a capability, not as a yield. In the first real
run with the slot (`runs/20260919_052152`) the yield was 0/3 ok reps: one got no
model at all, and the two models that ran both crashed (see the observation at the
end of §8). The PyChrono script is still never executed and nothing is derived
from it. The four behavioural dimensions of §6 (Behaviour, Robustness,
distribution test) are therefore defined for C only on reps whose DES slot
produced a contract, while Validity, Autonomy and Cost remain comparable across
every rep. What C is always scored on is structural recovery of the plant
(machine ids, process times, availability, buffer capacities, arrival rate — see
`kpis.native.machine_stats`), which A and B are also scored on via §6's Structural
dimension.

## 6. Metric dimensions and formulas

Per case `c`, method `m`, generation repetition `r ∈ 1..R`:

| Dimension | Metric | Formula |
|---|---|---|
| **Validity** | success rate | fraction of generations yielding a runnable model and parseable KPIs |
| **Behaviour** | indicator MAPE | `MAPE = mean over common indicators (|pred−truth|/truth)`; per-indicator MAPEs reported separately (throughput / WIP / utilisation* / energy*) |
| **Behaviour** | distribution test | 2-sample KS (or distance) between method's KPI values over its own R replications and truth KPI distribution over reference replications |
| **Structural** (secondary) | parameter error | for each recovered parameter `p` in `truth_structure.json`: `|pred−true|/true` (recovery quality; extraction is method-specific and best-effort) |
| **Robustness** | variance & outliers | std/IQR of `throughput_per_hour` across R generations; count of `simulation_error`/timeouts |
| **Autonomy** | human interventions | prompts answered by the harness + wall-clock time, logged |
| **Cost** | LLM usage | `llm_calls`, token estimate (see §7.5), wall time per generation |

`*` utilisation only meaningful where both truth and the method expose it; the
comparison for that indicator is restricted to the coverage intersection.

## 7. Experimental protocol

### 7.1 Standard run
For each configured case × method × rep: **generate → execute → parse → score**.
Truth artefacts are regenerated once per case (idempotent, seeded) if missing.

### 7.2 Repetitions
`config.yaml: repetitions` (default 1; recommend 3 for publication). Each rep is an
independent LLM generation with fresh seeds. `reference.replications` (default 10)
governs truth precision, independent of LLM cost.

### 7.3 Modes
- `mode: mock` — adapters skip LLM calls and return **canned models** built for the
  shipped case; the full generate→execute→parse→score path is exercised with no
  cost. Used for plumbing tests and CI.
- `mode: real` — adapters call the real toolchains (OpenRouter). Requires
  `OPENROUTER_API_KEY`, read from `.env` at the comparison root (edit that file
  to change it; an exported shell variable overrides it).

### 7.4 Steered mode (optional, future)
Baseline measures single-shot generation. A second pass ("steered") can be run
later: A regenerates with `run_manual_overrides` fed the truth-derived station
table; B runs `Modeloptimizer.optimize` on the measured bottleneck. Keep both modes
separate in reporting; never mix.

### 7.5 Cost accounting
The harness records `llm_calls` by counting client invocations per generation and
logs timings. For C the count is broken down in `kpis.native.llm_calls_split`
(`ui_agent` / `db_agent` / `dt_agent` / `harness_responder`), because C's figure
mixes *agent* calls with the calls the harness makes to its own customer-playing
LLM and, unlike A/B, C's own pipeline is where most of the spend sits — a single
total would be read as if it were comparable to a one-shot generator. The
split also survives retries: `agent_calls` counts service tasks that returned a
result (retries included) while `responder_calls` counts answers actually
produced, so a retry no longer inflates the derived responder count.
`llm_calls` is therefore a count of *answers*, and on a host that accepts work
and never finishes it (see §8) that understates the spend. For C the same split
is therefore also reported as attempts: `kpis.native.agent_tasks_attempted`
counts every submission to the service, including ones that failed or timed out,
against `agent_tasks`, the sum of the three *service-agent* entries of
`llm_calls_split` (`ui_agent` + `db_agent` + `dt_agent`), which counts only
answers. (The split has a fourth entry, `harness_responder`, so for real runs
`sum(llm_calls_split) == llm_calls == agent_tasks + responder_calls`; in mock
mode the three agent entries are `null`.)
Both are exact counts from the harness's own calls; nothing is inferred from the
service.
For exact token counts, run OpenRouter with a local HTTP proxy
(see `RUN_WITH_OPENROUTER.md` → dashboard at openrouter.ai/activity) or wrap the
client. Cost limits are enforced by `config.yaml` case/method/rep selection, never
by re-rolling.

### 7.6 Statistical plan
- Per-indicator MAPE is reported per case and aggregated as median [IQR] over cases.
- Pairwise method comparisons on each indicator use the **Wilcoxon signed-rank**
  over cases (paired by case). With A/B/C all present, a **Friedman** test per
  indicator plus Nemenyi post-hoc.
- KS per indicator across replications for the behaviour dimension.
- Minimum recommended design for publication: ≥ 5 cases, R = 3, reference
  replications ≥ 10. Power rises with case count; synthetic case authoring is cheap
  (§7.7).
- Significance threshold α = 0.05, two-sided, no multiple-testing corrections
  reported as corrected/unadjusted both.

### 7.7 Growing the case set
Add `cases/<id>/manifest.yaml` → run `casegen.py` → commit the generated artefacts.
The plant engine currently supports serial lines; parallel rows / rework loops /
defects / shift schedules are planned extensions (protocol §4 stays stable).

## 8. Adapter contract

Each adapter is a **standalone CLI**, executed in its method's venv by
`run_comparison.py`, and depends only on the Python stdlib plus its method's own
dependencies (`lib/` is stdlib-pure):

```
python adapters/<method>_adapter.py <mode=mock|real> <bundle_dir> <work_dir> <rep>
```

Contract: read `bundle_dir/manifest.json` (+ native input files); generate the
model (real: toolchain; mock: canned); write the model to `work_dir/model.py`;
execute it (subprocess, own venv, seeded) and parse KPIs; write
`work_dir/result.json` per §5; exit 0 on ok, non-zero on hard failure (still
writing `result.json` with the failure status). Errors on the *method's* side must
land in `result.status`, never crash the orchestrator.

C is the one exception to the `model.py` step: its artefact is a document, not a
program, so it writes `work_dir/model.json` (requirements + schema) plus an
`artifacts/` directory (see below) and has no execution stage
(`elapsed_simulation_s` stays `null`).

### Method A notes (`factoryflow_adapter.py`)
- Generation: `from IM.AMG_with_langgraph import run_amg_wrapper`; `cwd` = the
  Streamlit `app/` dir; `sys.path` prepended with the app dir and
  `app/src` (FactorySimPy is not pip-installed).
- Generated code is executed as a script in a fresh subprocess with a sanitising
  prelude: stub `streamlit` module injected into `sys.modules` (models copy the
  examples' `st.graphviz_chart` calls), `sys.path` insert for `factorysimpy/src`,
  `MPLBACKEND=Agg`. A probe appended after the model reads `Machine.stats`
  (`num_item_processed`, `total_time_spent_in_states`) from every machine of the
  top-level node, plus buffer content, and prints one tagged JSON line.
- Native horizon is read from the machine state-time sums (time unit per
  `config.yaml: A.model_time_unit_s`).
- **Availability has no library primitive, so it is the model's own problem.**
  `FactorySimPy` (both the `FactorySimPy/` and `FactoryFlow_v2/app/src` copies)
  contains no `mtbf`/`mttr`, no failure/repair/uptime/downtime concept and no
  unreliable-machine node — availability can only be hand-rolled by the generated
  code. The two real runs of `case_0001_serial_line` show both ways this can land,
  and the difference is not visible from the `ok`/`simulation_error` label alone:
  run `20260908_223442` **ignored availability entirely**
  (`Machine(env, id=…, processing_delay=delays[i])`, five machines, no failure
  logic) and still returned `ok` with a throughput of **19.9083 parts/h against a
  truth of 19.868056** — a 0.2 % error from a model with no availability at all,
  which is why the KPI alone cannot be read as evidence that the case was
  modelled; run `20260917_182936` **tried to model
  it and invented the API** — `Machine(env, id=data["name"],
  processing_delay=data["delay"], mtbf=mtbf, mttr=data["mttr"])` — which raised
  `TypeError: Machine.__init__() got an unexpected keyword argument 'mtbf'` and
  landed as `simulation_error` with all KPI cells `null`. An `ok` from this method
  therefore does not mean the case's availability was modelled; it means whatever
  the model chose to emit ran. Score the KPI, and read the generated code before
  attributing the KPI to the modelled system.

### Method B notes (`llmdes_adapter.py`)
- Runs in the LLM-DES venv; generation mirrors `main.py`'s headless path:
  `eventlog.load/preprocess/metrics.compute/to_sequence_text` on the case log,
  then `ModelBuilder(client).build(blueprint_code, stations_md, sequence_text,
  buffers, defects, manual_note)` with `aux_B.txt` supplying `buffers`/`defects`.
  `sim_time` and `warmup_seconds` come from the case's `reference` block as
  `warmup_s + window_s` and `warmup_s` (changed 2026-09-18 — the adapter used to
  pass config's `B.sim_time_s: 691200` / `B.warmup_s: 86400` regardless of the
  case, i.e. 7 days after a 1-day warm-up against a truth measured over 5 days
  after 6 h; those config values now serve only as the fallback for a bundle with
  no `reference` block). A key is honoured when it is *present*, including an
  explicit `warmup_s: 0`; truthiness would have swapped a legitimate zero warm-up
  for config's 86400. `replications` stays config-driven at 10: the reference's
  replication count is how precisely the *truth* mean is estimated, not a
  property B should inherit, and coupling them would vary B's internal precision
  per case.
- Execution reuses the repo's own runner: subprocess the model under
  `sys.executable`, parse the stdout contract
  (`Throughput = … parts/hour`, `WIP = … parts`,
  `Mean Energy Consumption per Part = … kWh/part`) exactly as
  `helpers.other_helpers.retrieve_KPIs` does.

### Method C notes (`method_c_adapter.py`)

C is driven entirely over HTTP against the deployment named by `API_URL` **in
`dtb_repo/.env`** (`config.yaml: dtb_repo`); the adapter reads that file rather
than duplicating the hostname, and exposes the resolved `api_url` in every
`result.json` so a run is traceable to the host it hit. Agents are addressed by
index and the mapping is configurable (`C.ui_agent_index`, `C.db_agent_index`,
`C.dt_agent_index`) because the service itself does not publish it; the shipped
values are the ones the method's own repo uses in `.env`, `config.py`,
`agents_starter.py` and `tests/agents/llm-responder.py` (`UI=0, DB=1, DT=2`).

- **Pipeline.** `POST /sessions` → `POST /conversations` (with C's own system
  prompt) → `POST /conversations/{id}/messages` → `POST /tasks` → poll
  `GET /tasks/{id}`. UI agent: interview loop until the reply's `completed` flag is
  true, or `C.max_interview_turns` is reached. DB agent: conversation seeded with
  C's `make_db_prompt(requirements)`. DT agent (agent 2): the method drives it
  through **three** conversation slots (`streamlit-app.py:290-384`) — slot 0 is

    `db_stage = "invalid_sql"` and **keeps its status**: the DB stage is a recorded
    property, and `derive_rep_status` is not allowed to read a gate's verdict — if it
    did, the amendment would be a route to making C look better by reclassifying
    reps, which is exactly what it must not be.

## 9. Running

```bash
# real mode only: key lives in `.env` (edit to change) — no export needed;
# `export OPENROUTER_API_KEY=sk-or-v1-...` also works and overrides .env
cd /ssd/projects/dt-eval/comparison

python run_comparison.py --mode mock                # plumbing, no cost
python run_comparison.py --mode real --cases case_0001_serial_line --methods A B
python run_comparison.py --mode real --repetitions 3    # full design
```

Orchestrator picks interpreters/cwds from `config.yaml`. Results and logs land in
`runs/<timestamp>/`; `report.py` renders `report.md` (+ optional PNG) into the same
folder. `casegen.py` is auto-run by the orchestrator whenever a bundle's generated
artefacts are missing.

Outputs per generation in `runs/…/<case>/<method>/rep<r>/`: `result.json`, the
generated `model.py`, the execution stdout/stderr log, and the A-assumptions text.
